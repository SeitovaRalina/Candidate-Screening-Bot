## D-18 — 5 self-sourced manual test pairs added; found and fixed a real em-dash false-positive bug in the AI-text heuristic
Anton's own 5 real resume+vacancy pairs (kickoff-followup item 7) are still outstanding, so Ralina built a stopgap set herself: 5 real, live, public hh.ru vacancy links (verified against `vacancy.py`'s actual fetch code, not just eyeballed) paired with synthetic-but-realistic resumes she authored (not scraped real candidates — see the honesty note in `prototype/tests/manual_cases/README.md` for why scraping real hh.ru resumes would itself violate the client's own PII stance, D-14, before the bot even exists). Each pair targets one scenario from `candidate-screening-criteria.md`: good fit, employer date overlap, skill/title mismatch (LLM-only), education/work overlap + gap together, AI-generated-sounding text.
Building case 5 surfaced a real bug: `check_ai_generated_text_pattern` counted em-dashes used as `"2020 — 2024"` date-range separators toward its dash-density signal, so almost any resume using that (very common RU-resume) date format false-triggered the flag on 2-4 dashes alone (cases 1-4 all falsely fired before the fix). Fixed in `deterministic_checks.py`: em-dashes inside a matched `_YEAR_RANGE_RE` span are now excluded from the count before computing the rate. Added `test_no_ai_flag_on_em_dash_date_ranges` as a regression test (existing fixtures all used a plain hyphen, which is why this wasn't caught earlier). These 5 pairs remain a smoke-test supplement, not a replacement for Anton's real acceptance set.
**Date:** 2026-09-04.

## D-20 — Small-talk short-circuit added; the bot is a workflow, not a chat agent, and now says so upfront
Manual testing (2026-09-04) surfaced a UX gap the client will hit immediately in a demo: `bot.py`'s `handle_message` is pure slot-filling (D-1's deterministic-workflow design) — any text goes straight into the empty vacancy or resume slot with zero interpretation, so "Привет! Что ты можешь?" was silently swallowed as "vacancy text" and got the generic "жду резюме" reply instead of an answer. Not a bug in the pipeline itself, but a bad first impression. Fix: `_looks_like_small_talk()` in `bot.py` — a short keyword/phrase check (not an LLM call, keeps the "no free-text intent routing" design intact) that only fires when both slots are still empty and the message is short (≤80 chars, a real pasted vacancy/resume essentially never is), and re-sends the `/start` greeting instead of consuming the message. Deliberately narrow: this is not a general chit-chat handler, just coverage for the one phrase a client predictably tries. Unit-tested in `tests/test_bot.py`.
**Date:** 2026-09-04.

## D-21 — Strict two-step flow (vacancy first, then resume), replacing "any order" — fixes a silent-wrong-answer bug, not just a UX complaint
Ralina reported (2026-09-04) that the two-message flow "не интуитивно понятно". Investigation found a real correctness bug behind the UX complaint, not just unclear copy: the old design accepted vacancy-text and resume-text "in any order", but had **no way to tell them apart** — whichever plain-text message arrived first was unconditionally treated as the vacancy (`vacancy.py`'s `fetch_vacancy()` accepts arbitrary text as a valid vacancy description with no validation), so a user sending the resume text first got a card built from swapped inputs with **no error at all**. Fixed: `bot.py` now enforces vacancy-first, fetches and confirms it immediately (`✅ Вакансия принята: {title}`) before asking for the resume, so the user gets visible proof of what was understood at each step and a vacancy-fetch error surfaces immediately rather than after the resume is already in. Trades the (illusory, already-broken) "any order" flexibility for correctness + a guided `/start` message with numbered steps.
**Date:** 2026-09-04.

## D-22 — Combined single-message input accepted (vacancy + resume together)
User request (2026-09-04, mid-review of D-21): "а вдруг человек захочет в одном сообщении все кинуть? Агент тоже должен это принять." Added `_try_split_combined_message()` in `bot.py`: a best-effort, non-LLM heuristic that looks for a resume-section header (reusing `deterministic_checks.py`'s own header vocabulary) appearing after a vacancy-marker keyword or hh.ru link, or an hh.ru link followed by a long freeform remainder — and screens immediately if it finds one, without waiting for a second message. Also handles a resume **file** sent with the vacancy text as its Telegram caption. Deliberately conservative (requires a vacancy-marker word before the resume header) specifically so a resume sent *alone* doesn't get its own name/education block wrongly carved off as a fake vacancy — verified in `tests/test_bot.py` that both a lone resume and a lone vacancy correctly return "no split" and fall through to the normal single-item path. Known blind spot, accepted for a same-day prototype: a resume that happens to mention a vacancy-sounding word (e.g. "обязанности" describing a past job) before its own experience section could still misfire — not silent data loss either way, both halves are still used as *something*, just possibly swapped.
**Date:** 2026-09-04.

## D-23 — LiteLLM gateway silently drops the LAST field of the tool_use schema; reordered the schema, added defensive .get() everywhere
Live-tested (2026-09-04) after Ralina reported a real card came back with green_flags/red_flags/interview_questions all empty despite `verdict=fit`. Root-caused, not guessed: an identical direct call using the exact same code (`screen_candidate`) against the exact same vacancy+resume (`tests/manual_cases/case-1-good-fit-resume.txt`) worked perfectly one time, then a follow-up run crashed with `KeyError: 'interview_questions'` - the payload was missing that key **entirely**, not just empty, despite it being listed in the schema's `required` array. Reordering the schema (moving `interview_questions` from last to before `red_flags`) and re-running 4x showed the dropped field always tracks the schema's last property, regardless of which field that is - confirmed by a throwaway test that swapped the order and watched `red_flags` disappear instead. This is a gateway/backend behavior, not model creativity: real Anthropic Claude reliably fills every `required` tool field; whatever actually backs the `claude-sonnet-5` alias on `llm.effective.land` (see D-19's `/v1/models` finding: `owned_by: openai`, response ids that decode to `litellm:custom_llm_provider:openai`, `reasoning_content` fields in raw chat-completions output - this is very likely not genuine Anthropic Claude under the hood) does not.
Two-layer fix in `screening.py`: (1) schema reordered so `red_flags` — the one field that's legitimately allowed to be empty — is last, since it tolerates being silently dropped far better than `green_flags`/`interview_questions` would; (2) every payload access changed from `payload["x"]` to `payload.get("x") or []` / `payload.get("x", default)`, since the "required" guarantee cannot be trusted on this backend at all, not just for the one field that happened to trigger the crash. Also added `minItems: 1` on `green_flags`/`interview_questions` in the schema and an explicit system-prompt rule forbidding empty green_flags/interview_questions, plus a one-retry safety net in `screen_candidate()` if both come back empty. **Residual risk, not fully closed:** this is a specific vendor/gateway quirk observed and mitigated for a 5-field schema; if the schema grows, re-verify which field is now last and whether it can tolerate being dropped, rather than assuming the fix generalizes automatically.
**Date:** 2026-09-04.

## D-24 — Hardened further: verify ALL required fields every time, hard-fail rather than ever render a possibly-incomplete card
Ralina rejected D-23's "sacrifice red_flags, it tolerates being dropped" framing outright: "нельзя терять поле, нужно, чтобы все были" — correct call, since a silently-dropped `red_flags` would render as "красные флаги: нет", indistinguishable from a genuinely clean candidate, which is exactly the kind of unsupported-verdict risk `project-rules.md` already forbids. Reworked `screen_candidate()`: every attempt now checks all 5 required keys are present (not just green_flags/interview_questions); a retry appends an explicit correction listing exactly which keys were missing and demands they come back, even as `[]`; after `_MAX_ATTEMPTS=3` failed attempts, raises `ScreeningIncompleteError` instead of returning any card — `bot.py` catches this specifically and tells the user to resend rather than showing a possibly-wrong result. Live-verified the failure path is real, not theoretical: a live run under concurrent load (several diagnostic scripts hitting the gateway at once) genuinely failed all 3 retries with every field missing every time, and the new code correctly refused to produce a card rather than rendering one with defaults - re-running the identical case in isolation immediately afterward succeeded cleanly (all 5 keys present), pointing at gateway-side load/contention rather than a permanent break. The D-23 schema reorder is kept as a cheap first line of defense (fewer retries needed in the common case) but the system's correctness no longer depends on it.
**Date:** 2026-09-04.

## D-25 — Order-independent input via content-based routing, not the D-21 positional guard (supersedes D-21's strict ordering)
Caught live by Ralina testing case-3 (2026-09-04): she sent the resume file first, and the bot's strict vacancy-then-resume rule (D-21) refused it with "сначала вакансия, потом резюме" - a file that plainly was a resume got rejected purely because of arrival order. She pushed back: "порядок отправления вакансии и резюме же не важен, мы же договорились" - and she's right that order independence was the actual goal; D-21's fix for the *original* swap bug (resume text silently misread as vacancy text) was a narrower, more defensive step than the real requirement.
Redesigned instead of reverting: `_detect_kind()` in `bot.py` classifies each plain-text message by content - an hh.ru link or a vacancy-marker keyword (`вакансия`, `требования`, `оклад`, ...) is a vacancy; a resume-section header (`опыт работы`, ...) with no vacancy marker is a resume; anything with neither is genuinely ambiguous and falls back to the D-11 positional default (first such message is the vacancy) since there's nothing to route it by. A file is unconditionally treated as a resume (nothing else is ever sent as a file here), so file-order was never actually ambiguous - that part of D-21's rejection was avoidable friction, not a needed guard. `handle_message` is now a single content-routed function instead of two step-specific handlers; the D-21/D-24 patch functions that guarded specific wrong-slot cases (resume-detected-as-vacancy, link-detected-as-resume) are gone because the new routing prevents them from being possible in the first place, rather than catching them after the fact.
Same-day, cheap heuristics only (regex, no LLM call) - deliberately not what Ralina originally floated ("определять по смыслу с помощью агента"): this gateway has demonstrated real reliability problems under load (D-23/D-24), and a per-message classification call would add both latency and a new failure surface for something the existing regex vocabulary (already built for D-22's combined-message split) already solves for the concrete cases seen. Residual limitation, same shape as D-22's: a resume using only English section headers ("Work Experience") with no Russian vacancy-marker keyword nearby would be genuinely ambiguous and fall back to the positional default - not a new gap, the same category already documented for the split heuristic.
**Date:** 2026-09-04.

## D-26 — Deployed to a persistent VPS (systemd), not just local; found and fixed a Python 3.14 asyncio incompatibility
Ralina confirmed (2026-09-04) Anton needs to reach the bot asynchronously ("жду прототип" implies independent testing, not only a live-controlled demo), so a laptop-only bot wasn't sufficient - deployed to a VPS she provisioned (Ubuntu 26.04) as a `systemd` service (`candidate-screening-bot.service`, `Restart=on-failure`, enabled on boot) so it survives her machine being off. Confirmed first that a public IP was never the actual requirement: `main.py` uses `run_polling()` (long polling, outbound-only), so no inbound port/public IP is needed for Telegram connectivity at all - the public IP only mattered for her own SSH access. Verified live that this specific server has unblocked outbound access to both `api.telegram.org` and `llm.effective.land` (`curl` reachability check before deploying), so `PROXY_URL` (D-19's Russian-server mitigation) was not needed here - kept in the code as a no-op fallback regardless.
Found live during deploy: the server's `python3.14` broke `python-telegram-bot==21.7`'s `run_polling()` - Python 3.14 removed the implicit main-thread event loop creation that `asyncio.get_event_loop()` used to fall back on, so the process crash-looped with `RuntimeError: There is no current event loop`. No older Python was available via `apt` on this box. Fixed in `main.py` by explicitly `asyncio.set_event_loop(asyncio.new_event_loop())` before `run_polling()`, rather than bumping library versions under time pressure and having to re-verify compatibility elsewhere. Verified stable (0 restarts, running 40+s) after the fix.
**Operational note:** `python-telegram-bot`'s long polling means only one process can hold a given bot token at a time - running the same token locally while the server instance is up returns `409 Conflict`. `systemctl stop/start candidate-screening-bot` on the VPS before/after local testing, or a second BotFather token dedicated to local testing, are the two ways to avoid this - no code change, just an operational note.
**Date:** 2026-09-04.

## D-27 — Three real bugs found via Ralina's own manual run of all 5 test cases against the deployed bot
She ran the full `tests/manual_cases/` set end-to-end and saved output to `test_results.md` (2026-09-04) - reviewing it surfaced concrete defects, not just calibration nits:
1. **Fake evidence quotes.** Case 3 (skill mismatch) had 4 of 11 red_flags with `quote: "нет"` - the model raising a flag for something *absent* (no portfolio link, no CV-tooling experience) has nothing to quote, so it filled the required `quote` field with a placeholder that reads exactly like a real citation. This directly violates the evidence rule (D-4, project-rules.md: "no unsupported verdicts") in a way that's invisible to a reader unless they check closely. Fixed: `_has_real_quote()` in `screening.py` strips any red flag whose quote is `""`/`"нет"`/`"n/a"`/`"-"`; system prompt rule 7 tells the model outright not to raise absence-only flags it can't cite.
2. **Interview questions rendered as raw Python dict reprs.** Case 5's card showed `1. {'text': "..."}"` instead of plain question text - the same backend unreliability from D-23/D-24 (doesn't respect declared JSON schema types) hit `interview_questions`' item type, not just top-level required keys. Fixed: `_as_question_text()` coerces a dict-shaped item to its `text`/`question` field before it ever reaches `card.py`.
3. **`[code]` marker broken by Telegram Markdown.** Case 2's card showed "...2021 — 2024 code" with the brackets silently stripped - `[code]` collides with Telegram's inline-link syntax `[text](url)`. Fixed in `card.py`: marker changed to a plain 🔧 emoji, no brackets involved.
Also addressed without being a hard bug: case 2 showed the same employer-overlap finding twice (LLM restated it with a different connector word - "и" vs the deterministic snippet's "/" - so the existing exact-quote dedup missed it); system prompt rule 5 now tells the model the deterministic findings are supplied for *context only* and are added to the card by code, not to repeat them at all, rather than asking it to copy quotes verbatim and hoping it complies. Also added rule 8 (cap red_flags to the handful that actually matter, and make sure each one generates a matching interview question) and rule 9 (a date overlap/gap alone shouldn't force `verdict=not_fit` if the rest of the resume is otherwise relevant - it's an interview question, not an automatic rejection) after noticing case 4 was marked "не подходит" purely on two date-consistency flags with no interview question addressing either of them.
New tests in `tests/test_screening.py` (pure functions, no API key needed) cover both extracted helpers directly.
**Date:** 2026-09-04.
